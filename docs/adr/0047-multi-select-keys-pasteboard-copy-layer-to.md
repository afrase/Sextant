# 47. Multi-select, the keys pasteboard type, and Copy Layer To

Status: accepted, 2026-10-14. v1 plan slice 2.2. Builds on ADRs 0027 (key inspector), 0028 (picker), 0037 (assign targets, EditSession hooks) and 0042 (macros).

## Context
Spec §5.4 asks for multi-selection: ⌘-click toggles a key, ⇧-click selects a range in reading order, the inspector says "3 keys" and every slot edit applies to all of them as one undo step. §5.5 adds ⌘C and ⌘V for keys ("Paste Key"), and §6.1 lists Copy Layer To… in the sidebar's context menu and the Layer menu. All three were placeholders. The user decided (plan question 8) that Copy Layer To works only within one layout: replace a layer's keys or add a new layer.

EditSession's key edits took one key: an explicit index, else `selection.keyIndex`. Extension files (tapping term, macros) already call `target(_:_:)`, and every view reads `keyIndex`. The pasteboard is outside Sextant's control: what another app, another Sextant build or a hand-made payload puts there reaches the layout, and keycodes end up in generated C.

## Decision
- **The anchor is `keyIndex`; the rest are additive.** `EditorSelection.keyIndices` lists every selected key, the anchor included, ascending. The other keys are private storage, and setting `keyIndex` to a different key drops them, so every existing path (arrows, a plain click, Find Key, Show Key, undo snapshots) keeps meaning one key without being touched. Setting it to the same key keeps them, so changing the slot (⇥, ⌥⌘1–4, the slot strip, ⌥⇥ in the picker) edits every selected key. `select(keys:anchor:)` and `toggle(key:)` are the only ways in. A ⌘-click on the anchor passes it to the lowest other key.
- **Edits act on the selection.** `targets()` returns the given key, else every selected key; `target(_:_:)` stays for one-key edits. Set action, set code (each key keeps its own chord), hold layer, modifiers, label, LED color, Make Transparent, Disable and Override (the inherited keys among them) loop inside one `edit`. One key keeps the single-key undo name, so the existing tests pass untouched; several get a count: "Make 3 Keys Transparent", "Set Tap on 3 Keys", "Clear Label on 3 Keys". Undo restores the multi-selection with the layout. Swap, Set Key, Record Key and the tapping term stay one-key (the anchor).
- **Where several keys can be selected:** the plain board in the Keys lens with no pick on. Elsewhere ⌘- and ⇧-click are plain clicks, and choosing another lens keeps only the anchor. Arrows and a drag collapse to one key; esc first collapses to the anchor, then deselects (a rung between §9.3 steps 4 and 5). ⌘ wins when ⌘ and ⇧ are both down.
- **The range follows VoiceOver's reading order** (left half row by row, its thumbs, then the right half and its thumbs), from the anchor to the clicked key, so a ⇧-click from the left half's last key to the right half's first takes no key in between.
- **The board** draws a ring on every selected key; only the anchor's glows while focused, and the picker preview still replaces the anchor's ring. Every selected key carries VoiceOver's selected trait, and a custom action "Add to Selection" / "Remove from Selection" stands in for ⌘-click.
- **The inspector** shows `MultiKeyInspector`: up to three caps fanned, "4 keys", the layer, and "Keys 13, 14, 15 and 16". A slot strip shows each slot's shared value or "Mixed". When the selected slot holds one value on every key, the ordinary `SlotEditor` edits it (its calls go to every selected key); when it differs, "Mixed: 4 different" with Change… and Clear. Then LED color (the swatch menu), Make Transparent, Disable, Copy To Layer ▸ and Clear Label. The context strip says "4 keys selected · ⌘-click adds or removes a key · esc keeps one".
- **The picker's default target becomes "4 keys › Tap on Main"** (`keySlotTarget`, ADR 0037). It still names the anchor as its key, so the picker floats clear of it, the board previews it and Suggested stays slot-aware. Assigning goes through `EditSession.setAction(slot:_:)`, which hands each key's current action to the picker's chord rule, so each key keeps its own chord exactly as one key does. The Macros category's rows call `assignMacroToSelectedKeys`: a draft moves onto the first key and the others get copies, as ADR 0042 assigns one key at a time, all in one undo step.
- **Cut, copy and paste** are SwiftUI's `onCopyCommand`, `onCutCommand` and `onPasteCommand` on the board, so they act on keys only while the board has focus and text fields keep the standard commands. They are off on a page and on History's read-only board; cut is off during a pick.
  - Copy writes the selected keys of the shown layer, as stored, through an item provider with two flavors: `com.sextant.keys` (JSON) and their QMK expressions as plain text ("KC_A, LT(1, KC_ENTER)"). A probe (its own offscreen window, with the general pasteboard redirected to a private one) confirmed that SwiftUI writes a provider's undeclared custom type to the pasteboard as is, and calls the paste action while that type is there. The type is declared in Info.plist (`UTExportedTypeDeclarations`, conforming to public.json).
  - Paste reads the pasteboard itself. One copied key goes onto every selected key ("Paste Key", "Paste onto 3 Keys"). Several go back to their own indices on the shown layer, which needs the same board and key count, and are then selected ("Paste 3 Keys"). Refused or unfitting keys beep and change nothing.
  - Cut is copy plus Make Transparent, one undo step ("Cut 3 Keys").
- **`CopiedKeys` (domain) is the trust boundary.** The JSON holds a format name, version 1, the board, its key count and `{index, key}` pairs, each key in Oryx's own key shape. Decoding refuses: more than 1 MB, another format or version, no keys or more keys than the board, a key count outside 1–256, an index off the board or repeated, a keycode or macro step that isn't a QMK identifier of at most 64 characters (it would land in generated C), and a layer outside QMK's 0–31. It clamps labels to 10 characters, descriptions to 30, macro names to 64, waits to 0–5 s, and drops a tapping term outside the generator's range. Macros keep every step: Oryx layouts hold longer ones than the 24 Sextant's editor makes (JRGQm has a 25-step macro), and the size cap bounds them. On paste, a layer key whose layer this layout lacks becomes `KC_NO`, as after Delete Layer. Refusals are logged by kind only; the payload never is, since macros can hold secrets.
- **Copy To Layer** (`copyKeys(toLayer:)`) puts the selected keys in the same places on another layer, one undo step ("Copy 2 Keys to Brd+Sys"), and stays on the shown layer so the keys can go to several layers.
- **Copy Layer To** is a submenu, shared by the Layer menu, the sidebar's context menu and the layer summary's "Copy To" button: every other layer of the layout, then New Layer. `copyLayer(_:to:)` replaces the target's keys and keeps its id, name and color; `appendLayer(copying:)` adds "Sym+Num Copy" at the end. Each is one undo step and shows the layer copied to. Layer keys keep their numbers, which mean the same layers within one layout. There is no `Library.copyLayer` (question 8). Being a submenu, it loses the spec's ellipsis.
- **Re-importing from Oryx keeps the layout's macro drafts** (`applyImport`). Oryx has no drafts, so the import used to drop them (ADR 0042's open consequence); the import revision records them too, so the document isn't "Edited" afterwards.
- **Files.** The multi-key edits that aren't single-key edits (the picker's per-key assignment, macro assignment, Copy To Layer, the pasteboard and Copy Layer To) live in `EditSession+MultiSelect.swift`, keeping EditSession.swift within the lint's file and type length limits. The window's click handling for ⌘ and ⇧ is `LayoutWindowModel+Selection.swift`.

## Consequences
- ⌘⏎ in the picker still moves to the next key in reading order, so after assigning to several keys it leaves one key selected.
- Record Key, Copy QMK Expression and Override's menu enablement still look at the anchor. Record Key writes only the anchor.
- A copy in one layout pastes into another layout's window: keys go by index, and layer keys keep their numbers there, or become `KC_NO` where that layer doesn't exist.
- Pasting several keys copied from another board refuses rather than guessing positions.
- The existing snapshot references are unchanged. A new board reference, light and dark, pins a ring on each of five selected keys across both halves and a rotated thumb (`mainWithSeveralKeysSelected`). New design-QA scenes, light and dark: `multiselect`, `multiselect-min` (1120×640), `multiselect-hold`, `multiselect-picker` and `layers-copy-menu`; `layers-color-menu`'s drawn menu now shows Copy Layer To as a submenu.
