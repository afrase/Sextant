# 44. Exports and Print: one save panel, a vector PDF instead of SVG, PDFKit in the UI layer

Status: accepted, 2026-10-12. v1 plan slice 1.4.

## Context
Spec §9.1 lists File ▸ Export ▸ Layout JSON…, QMK Source (.zip)…, Firmware (.bin)… (MVP, never built) and Image (PNG/SVG)…, plus Print Layout… (⌘P). The app had no file panel yet. Foundation has no SVG writer, so SVG means a hand-written exporter whose legends lose their SF Symbols. A PDF drawn by the same renderer as the board keeps the real legends and stays vector. The user chose PNG, a vector PDF and Print, with no SVG (2026-10-12).

## Decision
- **One save panel per window.** `LayoutWindowModel.pendingExport` holds the file waiting for its panel, or why it couldn't be made or saved. `ExportPresenter` (one line in `windowPresentations`) puts up one `.fileExporter` and one alert for every kind. `ExportFile` is a single `FileDocument` that carries its bytes, its content type and a suggested name. The plan said one document per type; one type that carries its type is smaller and does the same job.
  - The file is made before the panel opens, so writing it can't fail halfway, and a generator error shows before any panel does.
  - While a panel is open, the Export items are disabled. The panel writes whatever file is pending, so a second export would land under the first one's name.
  - While the window shows another sheet or alert, Export refuses with a beep. SwiftUI never shows a `.fileExporter` over another presentation, not even after that presentation closes, so the file would stay pending and every later export in the window would be stuck. The check is the main window's `attachedSheet`, because some sheets and alerts are view state the model can't see.
  - Failures are `ExportError` (`LocalizedError`): the board couldn't be drawn, the layout couldn't be encoded, or the source couldn't be zipped (with the system's reason). A generator error keeps its own text, and so does the panel's write error. The alert's title is "Sextant couldn’t export the layout".
  - The suggested name has no extension. The panel adds the content type's: the layout title for JSON, firmware and the PDF, "<title> QMK Source" for the zip, "<title> – <layer>" for the PNG. `/` and `:` become `-`.
- **Layout JSON** is the package's `layout.json` encoding: Oryx's revision shape, pretty-printed, keys sorted (architecture §2.1). It round-trips through `KeyboardLayout(oryxJSON:)`.
- **QMK Source (.zip)** is what a build compiles now. `BuildFlashSession.source()` runs the generator port with the identity a build would flash (ADR 0019), so the zip carries the same serial. The UI never holds the generator, and nothing new is wired. The files go in a folder of the same name, zipped by a coordinated read with `.forUploading`, so no zip library is needed. The temporary folder is removed afterward. The folder's name is transliterated to ASCII ("Café" becomes "Cafe"): the system's zip doesn't set the UTF-8 flag, so Windows Explorer, 7-Zip and Python would read any other name as CP437. Export doesn't refuse live errors: the source of a broken layout is still useful, and the generator refuses what it can't express.
- **Firmware (.bin)** is the window's last build, DFU suffix included. It is enabled only while the layout is still the one that build compiled (`BuildFlashSession.currentArtifact`), so after an edit you build again. Otherwise the image would miss the edits while QMK Source, next to it, has them. The system's `.bin` type is MacBinary's, and only its extension is used.
- **`BoardImage`** is one layer as a picture: the layout title, the layer's chip and name, `KeyCap`s on `BoardCanvas` and the `NavigatorDisc`, in the window's legend mode. It has no selection, issues, presses or activator halo, is always light, sits on white, and has a whole-point size that is the same for every layer. It uses Sextant's own geometry (`EditSession.geometry(of:)`, the window's own rule), with no ZSA art.
  - **Image (PNG)…** is the shown layer at 2x through `ImageRenderer`, marked 144 dpi so it opens at its point size.
  - **All Layers (PDF)…** draws each layer through `ImageRenderer.render` into a `CGContext` PDF, one page per layer. Titles, legends and SF Symbols stay text and paths. The caps cast no shadows here: `KeyCap` reads a `capShadows` environment value, and the PDF sets it to false. SwiftUI embeds each shadow as an image with a soft mask, and the print path (PDFKit's print operation, and so Preview's printing too) drops many of the masks, so the shadows printed as grey boxes. Without them a page is about half the size, and the edge stroke still outlines each cap. The PNG keeps its shadows.
- **Print Layout… (⌘P)** prints that same PDF with PDFKit's `printOperation(for:scalingMode: .pageScaleToFit, autoRotate: true)`, run as a sheet on the main window. It uses a copy of the shared print info set to landscape, because every page is wider than tall and portrait paper would show the boards sideways. That gives the system preview, page setup and Save as PDF. PDFKit joins the UI layer's allowed imports in `.swiftlint.yml`. It is a system framework, so nothing is downloaded.
- **No SVG.** The PDF stands in for it.

## Consequences
- Offscreen tests cover what can be tested offscreen: the PNG's pixel size, the PDF's page count (3 for KlgM7, 12 for JRGQm), its text and the absence of shadow images, the zip's files through the generator and its ASCII folder, a generator failure, a panel that opened while the source was made, the JSON round-trip, names, and enablement, including a stale build. A probe printed the PDFs through PDFKit to a file and confirmed the pages come out upright and without grey boxes. There is also a `BoardImage` reference image and the `export-image-light` scene. The save panel and the print sheet can't run offscreen: a probe confirmed the panel opens with the suggested name and type, and the user checks writing a file and ⌘P in the app.
- The PDF is drawn on the main actor because `ImageRenderer` is main-actor bound. In a debug build that takes about 0.6 s for a 12-layer layout, with no progress shown.
- The library row's Export ▸ (spec §2.3) is still missing. It would export a layout that isn't open, so it needs a session-less path; nothing asks for it yet.
- Slice 2.5's Export Source Zip… reuses `ExportFile`, `LayoutExport.zip` and `pendingExport`. It adds a layout parameter to `BuildFlashSession.source()` for the revision's layout.
