# 46. Combos: what "Active on" means, member rules, and how the lens draws

Status: accepted, 2026-10-14. v1 plan slice 2.1 (the Combos lens). Builds on ADR 0037 (pages, board picks, assign targets, the cap decoration hook, every combo issue kind) and ADR 0042 (a combo's output can be a macro).

## Context
Spec §6.4 asks for a Combos lens: combo keys ringed and numbered in the combo's colour, a trace joining them, an output pill that never covers a legend, everything else at 45%, a way to make a combo by clicking keys and choosing an output, and an inspector with an "Active on" choice and warnings.

QMK matches combos by keycode. Oryx stores a layer per combo (`layerIdx`), and its generated source lists the keycodes at the combo's key positions on that layer; the firmware then fires the combo wherever keys with those keycodes go down together, on any layer. A true per-layer restriction would need `COMBO_SHOULD_TRIGGER` code and would stop matching Oryx's output for JRGQm and m9dpx. The user chose to keep Oryx's meaning and describe it honestly (plan question 3).

Some keys can't take part in a combo. A transparent key's `KC_TRANSPARENT` is never reported as pressed: QMK reports the keycode of the layer below. `KC_NO` is `COMBO_END`, so it would end the key list early. The generator wrote both into the combo arrays. A tap dance's `TD()` does reach the combo engine (`process_combo` runs before tap dance in `quantum.c`), but Oryx refuses tap-dance combo keys (research 01, item 10), and the plan keeps that rule.

## Decision
- **A combo reads its keys from one layer; Sextant calls it "Keys from", not "Active on".** `Combo.keysLayer` is its layer, or the base layer when it has none (the generator already read nil as layer 0; every Oryx combo has a layer). The inspector's "Keys from" picker lists the layers, with the line "Sextant reads the keys at these spots on Main. The combo fires whenever keys typing the same keycodes go down together, on any layer." A new combo reads the layer shown when its output is chosen. There is no "All layers" setting on a combo: it would build the same firmware as the base layer.
- **The header's "Keys from: All layers ▾" is a filter.** It shows every combo on the shown layer's board, or only those reading one layer, which it then shows. The filter lives in the window (`CombosModel.showsAllLayers`), not in the document.
- **Member checks** (`LayoutIssues.comboIssues`, one call line in `check`):
  - more than 6 keys is `comboTooManyKeys`; fewer than 2 stays `emptyCombo` alone;
  - two combos listening for the same keycodes are `duplicateComboTrigger`, on both, whichever layers or spots they read them from: they compile to the same key list, so only one output can fire. A key's keycode is its one action (tap or hold), aliases as their catalog code; a mod-tap or layer-tap, which QMK writes as one shared keycode (`MT()`, `LT()`, `*_T()`; `Key.isModTapOrLayerTap`, the rule `QMKCodes.modTapOrLayerTap` builds by), is its tap and hold; any other dual-function key or a macro, which the generator numbers per key, counts as itself, so the check never flags two combos that build differently. Oryx's rule ("same layer, identical action sets") is narrower;
  - two keys of one combo typing the same keycode are `comboKeyRepeated` on the second: QMK's `_find_key_index_and_count` gives both presses the last matching place, so the combo never sees all its keys down. `KeyboardLayout.comboRepeatedKey` decides it for the check and the generator, which refuses "a combo with two keys that type the same keycode". Keys a combo can't use don't count: they have their own issue. (Added after the wave 2 integration review: the user's Sym+Num types * at two keys, and Copy Layer To and paste make repeats easy.)
  - `Key.comboRefusal` says which keys a combo can't use, and both the check and the generator use it: a key the generator writes as `KC_TRANSPARENT` (empty, or a transparent tap, with or without a label) is `comboKeyTransparent`; one written as `KC_NO` is `comboKeyDisabled`, a kind this slice adds to ADR 0037's list; a tap dance (a double tap or tap-then-hold) is `comboKeyTapDance`;
  - keys a fast typist rolls across in one motion are `rollingNeighbors`, a warning: all on one row of one half, each beside the next (`BoardGeometry.rollingPair`). The issue names the leftmost two ("J and K"). Keys on two rows, with a gap, or across the halves raise nothing.
  - JRGQm and m9dpx have no combo errors, so their builds aren't blocked; JRGQm gets rolling warnings.
- **The generator refuses what the checks flag,** in KeymapPlan's combo loop, on the key and by `Key.comboRefusal`, never by the token: "a combo key that is transparent", "… that is disabled", "… that is a tap dance". A test checks that a build fails on exactly the keys the live issues flag, so the build gate catches them first. The five goldens are unchanged.
- **Edits** live in `Layout+Combos.swift` (add, remove, toggle a key, set keys, output, layer, name; a seventh key, a key off the board and a layer that doesn't exist are refused) and `EditSession+Combos.swift`, one named undo step each ("New Combo", "Change Combo Keys", "Set Combo Output", "Change Combo Layer", "Rename Combo", "Delete Combo") that selects its combo, so undo brings the inspector back to it. Rename doesn't select: the name field commits as the user moves to another combo, and must not take them back. Undo that takes the combo under Edit Keys ends the draft.
- **Making a combo is a draft plus a board pick.** N, the strip's last card, the lane's New Combo or the inspector start a `BoardPick` ("Click 2–6 keys, then Choose Output · esc cancels"). Clicks add or remove keys in a `ComboDraft` held by the window, not the document, so a cancelled combo leaves no undo step and no empty combo behind. Choose Output (2–6 keys) opens the picker through an `AssignTarget`, "Combo 3 › Output", which takes a keycode, a layer key or a macro but not Transparent or No Action (either would make an empty combo). The choice makes the combo as one "New Combo" step and ends the pick; closing the picker without a choice keeps the keys. Edit Keys… is the same draft over an existing combo, kept with Done as one "Change Combo Keys" step. Esc, Cancel, another page or another layout drop the draft with its pick.
- **On the page, the board only reads keys.** A click selects a combo the key is in (the selected one if it has the key, else the lowest-numbered reading the shown layer, else the lowest-numbered), in `click(key:)`, so a key already selected still works; the arrow keys move the key and the combo follows (`moveSelection(_:)`). Only clicks and arrows run that rule, never a change to the selected key, so undo restoring a key outside the combo it saved keeps that combo. Selecting a combo by card, click, ⌘K or "Keys from" shows its layer; a card or a ⌘K row ends a New Combo or Edit Keys draft first. A selected combo counts only while the board shows its layer (`selectedPageCombo`): the board, inspector and ⌫ ignore it on another layer, so the filter or a layer switch never leaves it edited off screen. Esc goes back to every combo before it deselects the key. ⌫ deletes the selected combo instead of making the key transparent (one guard in BoardView's ⌫); painting and drag-to-swap are off; N starts a combo. VoiceOver's cap hint says a click selects a combo, and the key-editing actions are off on pages.
- **Drawing.** The caps' ring, number and 45% come from one case in `capDecoration` (`comboDecoration`). A selected combo is drawn alone; otherwise every shown combo is, and a key in several takes the lowest number while VoiceOver hears them all: "in combo 1: J + K → Escape; in combo 2: K + L → Return", by names rather than glyphs. With nothing to show, no key is dimmed. SF Symbols squeezes two digits past reading at 14 pt and circles numbers only up to 50, so from 10 the number is text in a filled circle (`CapDecoration.Mark.text` and `NumberDisc`, a small additive change to KeyCap, shared with the cards).
- **`ComboOverlay`**, one line in BoardView, draws in the board area's space:
  - the trace: the shortest tree joining each combo's key centres, 2 pt, with every cap cut out, so it shows only in the gaps. While several combos are drawn, a line that would pass under a cap outside its combo is left out (`ComboPills.trace`): what showed of it would end at that cap, which may be ringed for another combo, and read as joining it;
  - stray numbers: a key shows only the lowest of its combos' numbers, and lines under other caps are left out, so a combo could show nothing tying its keys to its pill (F + J where F and J are in lower combos). Each of its keys that no drawn line joins to a key showing its number gets the number beside the cap's own, along the top edge (`ComboPills.strayNumbers`, drawn with the cap's `MarkBadge`); pills avoid them like the cap's own;
  - the pill: the combo's number and its output as a cap shows it, black or white ink by the fill's luminance. `ComboPills.place` searches outward from just above the keys' bounding box, ring by ring on an eighth-of-a-key grid, out to six keys, and takes the first spot that covers no legend zone (a banded cap's band and the 70% above it, else its middle 60%, between the side paddings; a box around a rotated thumb's zone), no number badge, no Navigator and no other pill, inside the board area. A pill with no room is left out. JRGQm's 32 combos and a synthetic dense set of 32 on the user's layout all fit at a full window; a test checks both at full and minimum size, JRGQm only under `SEXTANT_REFERENCE`.
- **Colours** are the spec's 8 (§10.1), each darkened to 3:1 on the light bench and lightened to 3:1 on the dark cap, as layer colours are (`Tokens.combos`); combo n takes colour n − 1, round the palette. TokenContrastTests checks rings on the cap and both bench tones, and pill ink at 4.5:1.

## Consequences
- The sidebar gains Combos with its count; the destination routes to `CombosCanvas` and `ComboInspector`; the header, lane and context strip each gain a Combos branch; ⌘K's Documents group finds combos by name and keys.
- "Keys from" changes which keycodes a combo listens for, never where it fires. Matching Oryx's builds stays exact; a real per-layer restriction can come later as its own setting.
- The inspector's "Firmware Settings ›" link targets the Combos section, which the page shows once slice 2.3 drops its core-only filter.
- In the overview a combo of keys far apart may show no trace and its keys may carry other combos' numbers; its number then sits beside theirs on those keys, so each of its keys still shows it, and selecting it draws it whole. A key can carry two or three numbers on a busy board. A drawn-alone trace between distant keys still shows only in the gaps, but the only ringed caps are its own.

## Amendment, 2026-10-15: combo actions in the menus (spec §9.1, §11)
- Spec §11 says every action is reachable from a menu. Edit ▸ Delete, AppKit's standard item, deletes the selected combo on the Combos page: `CombosCanvas` answers it with `onDeleteCommand`, off with no combo selected or during a board pick (`comboForKeys`). The item shows plain ⌫ (`DeleteMenuItem`). Its key equivalent is U+0008, and the Mac's ⌫ sends U+007F, so the key still goes to the focused view first: a text field deletes text, and the page's own ⌫ deletes the combo, once.
- The Edit menu gains the page's section after the pasteboard group: New Combo and Edit Combo Keys…, each enabled only on the Combos page with something to act on, outside a board pick. ⌘K gets matching rows, plus Delete Combo (⌫). They call the page's own methods (`startNewCombo`, `editComboKeys`, `deleteCombo`), so nothing behaves differently. N still works only with the board focused: a plain letter as a menu shortcut would take typing.
