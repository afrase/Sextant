## 0. Summary

1. **ZSA has not published Voyager hardware.** Nothing was found for the Voyager or the Moonlander:
   - no schematic, PCB, case files or teardown;
   - no FCC filing (searched the web and all 17 public `github.com/zsa` repos).
   - The only ZSA hardware documents in the open are the **ErgoDox EZ V4/V5 schematics** (`zsa/docs`, 2017).
   - Everything known about the Voyager's electronics comes from the open QMK keyboard definition (GPL-2.0) and from one community Rust port.

2. **Voyager electronics, as the firmware sources describe them:**
   - One MCU on the left half: STM32F303**xB**-class, 128 KB flash, 32 KB RAM. The ZSA DFU bootloader occupies the first 8 KB, so the app gets 120 KB.
   - A **MCP23018** I/O expander (I2C 0x20) scans the right half.
   - **Two IS31FL3731** LED drivers: 0x74 for left LEDs 0-25, 0x77 for right LEDs 26-51.
   - 4 status LEDs: 2 on MCU pins, 2 on the expander.
   - All of these share I2C1 (PB6/PB7). The right half reaches it through a 90 cm **TRRS** cable (INFERRED: I2C plus power over the TRRS, the same as ZSA's published ErgoDox EZ design).
   - The QMK matrix is **12 rows x 7 cols**: rows 0-5 left, rows 6-11 right. 52 of the 84 cells are populated.
   - **Oryx key index N = QMK label `kNN` = RGB LED index N**, for all 52 keys.
   - The `LAYOUT()` macro takes its arguments in a **row-interleaved** order, so a macro argument position is *not* the Oryx index (§2.4).

3. **The open split boards differ from the Voyager in several ways:**
   - **Corne** (foostan/crkbd) is 3x6+3 per half, 42 keys. It has an MCU in **each** half joined by a serial link, where the Voyager has one MCU plus an expander. Its hardware is CC BY 4.0 / MIT.
   - Sofle (MIT), Lily58 (MIT), Kyria (CC BY-NC-SA 4.0) and Ferris/Sweep (Solderpad 2.1) all ship QMK definitions, VIA definitions, Vial definitions and ZMK shields with Studio support.
   - **The Ferris 0.2 matches the Voyager's topology**: an STM32 plus an MCP23017 expander.
   - The firmware hides every topology behind one matrix. A configurator therefore needs only **matrix + physical geometry + LED map**, and a generic model for Sextant is cheap (§3.4).

4. **The four open configurators have four different architectures:**
   - **QMK Configurator** compiles in the cloud and never talks to the device. It has no licence file.
   - **VIA** edits the keymap live over raw HID (32-byte reports on usage page 0xFF60). It looks keyboards up in a central definition database by VID/PID. GPL-3.0.
   - **Vial** uses VIA's transport plus a `0xFE` command prefix. The keyboard *sends its own* LZMA-compressed definition, and a physical "unlock" gesture gates risky operations. GPL-2.0.
   - **ZMK Studio** sends protobuf RPC over CDC-ACM serial or BLE GATT, framed with 0xAB/0xAC/0xAD. Behaviours and physical layouts are self-described by the device. MIT messages, Apache-2.0 app.
   - Their protocols and data formats are reusable. Their GPL code is not reusable in a closed app (§4.7).

5. **The Voyager can run open "live-edit" firmware today:**
   - **Vial**: an official vial-qmk keymap, added 2025-04-11. It has no RGB UI and no Navigator support.
   - **RMK** (Rust): it speaks the Vial protocol and adds per-key RGB effects. Its author says the board carries a **GD32F303CB**.
   - **VIA** only as a do-it-yourself build: no official keymap or definition exists, and VIA lists only the Moonlander, as "Unsupported by ZSA".
   - All of them flash through ZSA's DFU bootloader (`3297:0791`), and re-flashing an Oryx `.bin` reverts them.
   - **A Sextant that also speaks VIA and Vial would work with Cornes and with thousands of other boards.** The VIA repo has 2,029 v3 definitions and vial-qmk has 634 `vial.json` files.
   - The user would lose the Oryx-specific features listed in 03 §7.7: per-layer RGB maps, the Oryx live protocol, Keymapp, Navigator (in the existing ports), Smart Layers and Oryx cloud history (§5.3).

### 2.3 How the two halves become one 12x7 matrix

Left half (`matrix.c` lines 108-176):
- For `row` 0-5, the code drives `B10+row` HIGH and reads columns `[A0, A1, A2, A3, A6, A7, B0]` into bits 0-6 of `matrix[row]`.

Right half (`matrix.c` lines 133-137 and 178-204):
- For strobe `n` = 0-6, the code writes Port A `0x7F & ~(1<<n)`, driving GPA*n* LOW.
  - The same write puts the two status-LED bits on Port B.
- It then reads GPB0-5 and inverts the result, giving `raw_right[n]`.
- Finally it transposes:

```
matrix[11 - r] bit c  =  raw_right[6 - c] bit r        (r = 0..5, c = 0..6)
=>  matrix row R (6..11) is sensed on MCP GPB(11 - R)
    matrix col C (0..6)  is strobed on MCP GPA(6 - C)
```

`jpds/rmk-zsa-voyager` `src/mcp23018.rs` lines 1-10 confirms this independently ("logical row = 11 - sense_bit, logical col = 6 - strobe_bit").

**Swap hands.** `hand_swap_config` (`voyager.c` lines 204-219) mirrors each key to its counterpart. Every entry is a `keypos_t {col,row}` (upstream `quantum/keyboard.h` lines 30-33). The resolved mirror for each key is in the `swap_hands_target_*` fields of the JSON.

### 2.4 Oryx key index -> matrix -> LED index (all 52 keys)

How the identity was established. The generator checks every one of these programmatically for every key:
- QMK labels `k00`..`k51` in `layouts.LAYOUT.layout`: ZSA fork `keyboard.json` lines 163-214; upstream lines 160-211.
- `rgb_matrix.layout[N].matrix` equals the matrix of label `kNN`: ZSA fork `keyboard.json` lines 103-154. So **LED index N = label kNN**.
- Oryx's `keys[]` array uses the same order. The user's layer-0 keys line up with the generated `keymap.c` (`downloads/layout-source/unzipped/.../keymap.c` lines 21-26). For example, index 24 is `LT(1,KC_ENTER)` and index 51 is `LT(2,KC_SPACE)`.
- Report 03 §3.6 reached the same result from the Oryx web bundle and from `zsa/kontroll`.

**Pitfall: `LAYOUT()` argument order is not Oryx order.**
- QMK generates the macro arguments in the order of the `layouts.LAYOUT.layout` array.
- For the Voyager that array is row-interleaved: `k00..k05, k26..k31, k06..k11, k32..k37, ..., k24, k25, k50, k51`.
- Oryx's own `keymap.c` emits `LAYOUT_voyager(...)` in that order (`keymap.c` line 21: `DUAL_FUNC_0, KC_1 ... KC_5,` then `KC_6 ... KC_MINUS`).
- The `layout_macro_arg_index` column below gives the conversion:

`LAYOUT` argument order, as Oryx indices: `0-5, 26-31, 6-11, 32-37, 12-17, 38-43, 18-23, 44-49, 24, 25, 50, 51`.

### 2.5 What this means for Sextant

1. **Use the matrix position as the canonical key identity inside the app, and treat "Oryx index" as a per-board view.** The three ecosystems address keys differently:
   - Oryx JSON and Oryx RGB use the index (N).
   - The Oryx live protocol reports matrix (col,row) (03 §3.4).
   - VIA and Vial use (layer,row,col) and buffer offsets.
   - ZMK uses a linear "key position" in physical-layout order.
2. Ship `voyager-matrix-led-map.json` (or a Swift table generated from it) as the built-in Voyager definition. Its LED index equals the Oryx index, so no LED remapping is needed for per-key colours.
3. The 32 unused matrix cells must be preserved, as `KC_NO`, when reading or writing VIA buffers. Keys 23 and 44 sit in rows 4 and 10, outside the "obvious" 4-row block.

### 3.2 Corne vs Voyager, concretely

| Aspect | Voyager | Corne (crkbd) |
|---|---|---|
| Alpha block | 4 rows x 6 cols per half, including a number row | 3 rows x 6 cols per half (no number row). The 3x5 variant drops the outer column. |
| Thumbs | 2 per half, rotated in Oryx's renderer (03/01). Upright in QMK metadata. | 3 per half. The innermost is 1.5u tall in QMK and ZMK metadata (`crkbd/info.json` line 70; ZMK `6column.dtsi` `100 150` entries). |
| Stagger | column stagger, `y` 0 to 0.5u (`keyboard.json` lines 163-214) | column stagger, `y` 0 to 0.3u (`crkbd/info.json` lines 32-74) |
| Electronics | one MCU; the right half is a "dumb" expander | two MCUs; each half scans its own matrix and they sync over serial (`split.transport.sync.matrix_state`) |
| Handedness | fixed: the left half is always the master (it has the MCU) | configurable (`MASTER_LEFT`, `EE_HANDS`, or a handedness pin on v4: `split.handedness.pin GP21`) |
| Reflash | one firmware image, one DFU target | **both halves must be flashed** (foostan rev4 docs line 37: "follow the same procedure for the other side") |
| LED order | LED index = Oryx index; the right half mirrors the left | `split_count [27,27]` / `[23,23]`. The LED order follows wiring and includes underglow on rev1. |

For a configurator the differences reduce to: key count, geometry, matrix, LED map, and whether there are one or two flash targets.

### 3.3 Topology classes (why the configurator does not care)

| Class | Examples | What the host sees |
|---|---|---|
| A. One MCU + I2C expander over the cable | ErgoDox (EZ), Moonlander, Voyager, Ferris 0.2 | one USB device, one matrix |
| B. Two MCUs, wired serial or I2C link | Corne, Lily58, Sofle, Kyria, Sweep | one USB device (the master half), one merged matrix (QMK `split`) |
| C. Two wireless MCUs (ZMK central/peripheral) | nice!nano Cornes, Sweeps | one BLE or USB device; Studio talks to the central |

All three expose one keymap over one matrix. Sextant's model therefore needs no "split" concept beyond a `hand` attribute on each key and an optional `flashTargets` count (**INFERRED**).

### 3.4 A generic split-keyboard geometry model for Sextant

How each format describes geometry:

| Concern | Oryx (implicit) | QMK `info.json`/`keyboard.json` | KLE (VIA / Vial `layouts.keymap`) | ZMK physical layout (devicetree / Studio) |
|---|---|---|---|---|
| Unit | CSS grid fr units (01/03) | key units (1u), absolute `x,y,w,h` | KLE cursor model (relative `x`/`y` offsets per row) | **centi-key-units** (100 = 1u); rotation in centi-degrees (thumb `1200` = 12°) (**INFERRED** from values) |

Proposed Sextant model (**INFERRED**, a design suggestion):

```swift
struct KeyboardDefinition {          // one per board (or per firmware variant)
  var id: String                     // e.g. "zsa/voyager"
  var usbIDs: [(vid: UInt16, pid: UInt16)]
  var matrix: (rows: Int, cols: Int)
  var keys: [PhysicalKey]            // in the board's canonical "logical" order (Oryx order for ZSA boards)
  var leds: [LED]                    // LED index -> matrix/key, x/y (0..224, 0..64), flags
  var flashTargets: Int              // 1 for Voyager, 2 for Corne
}
struct PhysicalKey {
  var matrix: MatrixPos              // canonical identity
  var rect: (x, y, w, h: Double)     // key units, absolute, top-left origin
  var rotation: (deg, rx, ry: Double)
  var hand: Hand                     // .left / .right / .either
  var cluster: Cluster               // .alpha / .thumb / .extra
  var ledIndex: Int?
  var encoder: (index: Int, dir: Int)?
}
```

Importers:
1. QMK `info.json` from `keyboards.qmk.fm/v1/keyboards/<kb>/info.json`. This has all 3,760 QMK boards, including `zsa/voyager` and every `crkbd/*`; `keyboard_list.json` was fetched 2026-10-11.
2. KLE from VIA v3 definitions or a Vial `get_def`.
3. ZMK `PhysicalLayouts` over Studio RPC.
4. Oryx geometry (built in for ZSA boards).

All four map losslessly into this struct, except QMK's missing rotation. For rotation, take KLE or ZMK data where it exists.

### 4.2 QMK Configurator + QMK API (cloud compile, no device I/O)

- **Endpoints.** `.env.production` lines 1-2 set `VITE_API_URL=https://api.qmk.fm` and `VITE_KEYBOARDS_URL=https://keyboards.qmk.fm`. `src/store/modules/constants.js` lines 12-19 derive from them:
  - `/v1/keyboards`
  - `/v1/keyboard_list.json`
  - `/v1/compile`
  - `/v1/skeletons`
  - per-keyboard `info.json` (`src/store/modules/app/actions.js` line 134)
- **Compile request.** `src/api.js` lines 15-45 POSTs `{...template, keyboard, keymap, layout, layers}`. The template is `{version: 1, documentation: ...}` (`src/store/modules/keymap.js` lines 30-35).
  - The response holds `job_id`; the client then polls `GET /v1/compile/<job_id>`.
  - The payload rule: "Each layer is a single list of QMK keycodes the same length as the keyboard's `LAYOUT` macro" (`qmk/qmk_api@a38ab32` `docs/api_docs.md` lines 11-24).
  - **For the Voyager, that means `LAYOUT` argument order, the interleaved order of §2.4, not Oryx order.**
- **Server.** Flask API → Redis Queue → workers. A worker makes "a fresh qmk_firmware checkout", builds `keymap.c` from the layers, compiles, zips the source, and uploads both to MinIO (`docs/development_overview.md` lines 11-24). Downloads are `/v1/compile/<id>/hex` and `/source` (lines 38-44).
- **Limits.**
  - It builds **upstream QMK master** only, with no ZSA modules, so no Oryx protocol and no Navigator.
  - It accepts **layers only**: no tap dance, combos, `config.h` or custom C. It cannot express what Oryx emits (per-layer `ledmap`, `DUAL_FUNC` hold-taps, custom RGB keycodes).
  - **INFERRED** from the payload schema.
  - `zsa/voyager` is in `keyboard_list.json` (fetched 2026-10-11), so it *can* compile a plain Voyager firmware.
- **Tester.** It uses browser key events (`src/store/modules/tester/codeToPos.js`), not HID.
- **Reuse for Sextant:**
  - The concept "keymap JSON → remote compile → binary" is the pattern Oryx also uses (`hexUrl`/`zipUrl`).
  - The QMK API can serve as a public compile service for *upstream* builds.
  - **Do not copy code: there is no licence.** The keycode data is better taken from QMK's own hjson (§4.7).

### 4.3 VIA (live editing over raw HID, central definitions)

**Transport** (`the-via/app@935106a` `src/utils/keyboard-api.ts`):
- Report ID 0x00 (line 18).
- Each command is padded to **33 bytes**: report ID plus 32 payload bytes (lines 766-772).
- Commands are serialised through a per-device queue (`globalCommandQueue`, lines 194-196, 651-652).

**Discovery and identification:**
- WebHID filter: usage page `0xff60`, usage `0x61` (`src/shims/node-hid.ts` line 23). The filter also includes the QMK console page `0xff31`/`0x74`.
- Definition key: `vendorId * 65536 + productId` (`src/utils/hid-keyboards.ts` lines 6-9).
- Definitions are fetched from `/definitions/supported_kbs.json` and `/definitions/v3/<vpid>.json` on the app's origin (`src/utils/device-store.ts` lines 77, 125). They are built from the `the-via/keyboards` repo, which holds 2,029 `v3/**/*.json` at `9e3e9f4`.
- If the VID/PID has no definition, the user must sideload JSON in the Design tab (en.json line 364).

**Definition format v3** (`@the-via/reader` `src/types.v3.ts` lines 28-44):
- Top-level fields: `name`, `vendorId`, `productId`, `matrix {rows, cols}`, `menus`, `keycodes`, `customKeycodes`, `layouts {keymap: KLE, labels, presets}`.
- KLE legend slots: 0 = `row,col`; 4 = `e<n>` (encoder); 6 = `l<n>` (LED index); 8 = `group,option` (layout option) (`src/kle-parser.ts` lines 37-38, 230-277).

**Protocol:**
- See 03 §7.3 for the command table.
- Additions found in source:
  - The app now knows **`UI_SYNC_REQUEST = 0x16`**, parsed from device-originated buffers (`keyboard-api.ts` lines 45, 80-120). Upstream QMK's `via.h` enum stops at `0x15` (`quantum/via.h` lines 55-76), so this is app-ahead-of-firmware. **INFERRED**: ignore it for now.
  - **`get_keyboard_value` id `0x06` = keycodes version.** This came in with VIA protocol **0x000D**, in upstream `via.h` lines 42, 85. It returns `QMK_KEYCODES_VERSION_BCD`, which is `0x00000009` upstream (`quantum/keycodes.h` lines 29-33).
- Protocol versions differ across firmware trees, which matters for Sextant's version negotiation:

| Firmware tree | `VIA_PROTOCOL_VERSION` | QMK keycodes version | Source |
|---|---|---|---|
| upstream QMK master | 0x000D | 0.0.9 | `quantum/via.h` line 42; `quantum/keycodes.h` lines 29-30 |
| ZSA fork firmware25 | 0x000C | 0.0.7 | ZSA fork `quantum/via.h` line 42; `quantum/keycodes.h` (fw25 sparse) lines 29-30 |
| vial-qmk | 0x0009 (+ Vial protocol 6) | (vial-gui keycodes v6) | vial-qmk `quantum/via.h` line 42; `quantum/vial.h` line 25 |

**Keycode numbering is versioned.**
- VIA picks a dictionary from the protocol version: v10, v11 or v12 for protocols 10-12. For protocol ≥ 13 it requires the keycodes version (`src/utils/key-to-byte/dictionary-store.ts` lines 7-33). The app supports keycode versions 8-9 only (`keycodes-version.ts` lines 34-35).
- Example: v13 removes `RGB_*` and adds `UG_TOGG = 0x7820 ...` and `RM_TOGG = 0x7842 ...` (`key-to-byte/v13.ts` lines 3-50).
- **Sextant needs per-version keycode tables.** The ZSA fork (0.0.7) and upstream (0.0.9) already differ in the lighting range.

**Per-key RGB in VIA:**
- Implemented as **custom channel 0, value 1**:
  - set: `07 00 01 <led> 01 <hue> <sat>`, then `09 00` to commit;
  - get: `08 00 01 <led> 01`, reading H and S at bytes 5-6.
- Sources: `keyboard-api.ts` lines 19, 430-463; `src/utils/use-color-painter.tsx` lines 37-48.
- Keys carry `li` (LED index) from KLE slot 6.
- It is **single-layer and HS-only**, and the firmware must implement it in `via_custom_value_command_kb` (**INFERRED**: no such handler exists for the Voyager). It is not a replacement for Oryx per-layer `ledmap`.

**Picker UX.** Categories are Basic, Lighting, Media, Macro, Layers, Special, QMK Lighting and Custom (`src/utils/key.ts` lines 421-1087). There is an "Any" keycode text box with autocomplete (`autocomplete-keycodes.ts`).

**Status for ZSA boards:**
- Only `v3/zsa/moonlander.json` ("Moonlander Mark I (Unsupported by ZSA)", VID 0x3297, PID 0x1969, menus `qmk_rgb_matrix`) and `v3/ergodox_ez/ergodox_ez.json` (PID 0x4974) exist.
- `qmk_userspace_via` has `keyboards/zsa/moonlander/keymaps/via` and `keyboards/ergodox_ez/keymaps/via`, but **no Voyager**.
- Upstream QMK master has **0** `keymaps/via` directories; VIA keymaps moved to `the-via/qmk_userspace_via`, which has 2,203.

### 4.4 Vial (VIA transport, self-describing firmware, unlock gate)

**Discovery** (`vial-gui@aef8222` `src/main/python/util.py` lines 20, 70-133). A device is accepted when it is raw-HID (0xFF60/0x61) **and** one of these holds:
- its USB **serial number contains `vial:f64c2b3c`**; vial-qmk sets this in `builddefs/build_vial.mk` line 15;
- or its VID*65536+PID is in the bundled VIA definitions ("VIA stack"), so **vial-gui also drives plain VIA boards**;
- or it was sideloaded;
- or it is a `vibl` bootloader.

**Definition download** (`protocol/keyboard_comm.py` lines 114-145):
1. `FE 00` returns `<u32 LE vial_protocol><u64 keyboard_uid>`.
2. `FE 01` returns `<u32 LE size>`.
3. `FE 02 <u32 LE block>` returns 32-byte blocks.
4. Concatenate the blocks and LZMA-decompress to get `vial.json`.
- This is compressed by `util/vial_generate_definition.py` line 18 (`lzma.compress`).
- **The `vendorId`/`productId` inside `vial.json` are not used for matching.** The Voyager's `vial.json` says `0x4C4B`/`0x4643` while the firmware enumerates as `0x3297`/`0x1977` (vial-qmk `keyboards/zsa/voyager/keymaps/vial/vial.json`; `keyboard.json`).

**Unlock** (security):
- While locked, firmware refuses:
  - matrix-state reads ("wannabe keylogger", vial-qmk `quantum/via.c` lines 250-255);
  - macro writes (lines 400-405);
  - bootloader jump (lines 434-446);
  - assigning `QK_BOOT` (`quantum/vial.c` lines 80-84).
- While an unlock is in progress, only `FE 00/01/02/05/06/07` are processed (`via.c` lines 214-222).
- The unlock itself:
  1. Host sends `FE 06` (start).
  2. Host polls `FE 07`.
  3. Each poll decrements a counter from **50** (`VIAL_UNLOCK_COUNTER_MAX`) when ≥ 100 ms have passed **and all combo keys are held** (`vial.c` lines 27, 164-191).
  4. The poll reply carries `[unlocked, in_progress, counter]`.
- vial-gui polls every 200 ms (`unlocker.py` lines 46, 65-71, 89). That makes about 10 s of holding (**INFERRED** arithmetic); the floor is about 5 s.
- `FE 05` returns the combo key positions: up to 15 (row,col) pairs from byte 2, with 255 meaning unused (`keyboard_comm.py` lines 469-483).
- The Voyager's combo is matrix (11,5)+(11,6), Oryx keys 50+51 (vial-qmk `keyboards/zsa/voyager/keymaps/vial/config.h`).

**VialRGB** (new vs 03). It rides on VIA's lighting commands 0x07/0x08/0x09 (vial-qmk `quantum/via.c` lines 310-362; `quantum/vialrgb.h` lines 7-22; `quantum/vialrgb.c` lines 90-191). All multi-byte values are **little-endian**, unlike VIA's big-endian values.

| Dir | Bytes | Meaning |
|---|---|---|
| get | `08 40` | info: protocol (u16 LE, =1), max brightness |
| get | `08 41` | mode: id (u16 LE), speed, h, s, v |
| get | `08 42 <from u16 LE>` | supported effect ids |
| get | `08 43` | LED count (u16 LE) |
| get | `08 44 <led u16 LE>` | x, y, flags, matrix row/col (or 0xFF). (Firmware bug: high byte read as `args[1] >> 8`; harmless below 256 LEDs.) |
| set | `07 41 <id u16 LE> <speed> <h> <s> <v>` | set mode, not saved |
| set | `07 42 <first u16 LE> <n> {h s v}×n` | **direct mode**: up to 9 LEDs per report, clamped to max brightness |
| save | `09 ...` | `eeconfig_force_flush_rgb_matrix()` |

- Direct mode lets the **host paint per-key colours live**, which is equivalent to Oryx's `RGB_CONTROL` takeover.
- The vial-qmk **Moonlander** port enables it (`keymaps/vial/rules.mk`: `VIALRGB_ENABLE = yes`; `vial.json` `"lighting": "vialrgb"`). The **Voyager** port does not (`"lighting": "none"`).

**Keycodes.** vial-gui ships `keycodes_v5.py` and `keycodes_v6.py`, selected by Vial protocol (`keycodes/keycodes.py` lines 108-113). It defines `Keycode(qmk_id, label, tooltip, masked, alias, requires_feature)` (line 19).
- Masked codes such as `LSFT(kc)` and `LT(n,kc)` are composed by the picker.
- Tabs: Basic, ISO/JIS, Layers, Quantum, Backlight, App/Media/Mouse, MIDI, Tap Dance, User, Macro (`tabbed_keycodes.py` lines 163-185).

**Features compiled in by default:** QMK settings, tap dance (with per-key tapping term), caps word, combos, key overrides, layer lock, repeat key, Chordal Hold (`build_vial.mk` lines 4-33). See 03 §7.4 for the dynamic-entry wire format.

### 4.5 ZMK Studio (protobuf RPC, behaviours self-described)

**Transports** (`zmk/docs/docs/development/studio-rpc-protocol.md` lines 13-31; `zmk-studio-ts-client` `src/transport/serial.ts` line 7, `gatt.ts` lines 4-5):
- USB **CDC-ACM serial**. The firmware must be built with the `studio-rpc-usb-uart` snippet (`docs/docs/features/studio.md` line 78).
- **BLE GATT**: service `00000000-0196-6107-c967-c5cfb1c2482a`, characteristic `00000001-0196-6107-c967-c5cfb1c2482a`.

**Framing:**
- SoF `0xAB`, Esc `0xAC`, EoF `0xAD`.
- Any special byte in the payload is prefixed with Esc (`zmk-studio-ts-client` `src/framing.ts` lines 1-3).

**Messages** (`zmk-studio-messages@6cb4c28` `proto/zmk/*.proto`, MIT):
- `Request {request_id; oneof core|behaviors|keymap}`.
- `Response {oneof request_response|notification}` (`studio.proto` lines 11-43).
- core (`core.proto` lines 5-36): `get_device_info` (name, serial), `get_lock_state`, `lock`, `reset_settings`; plus a `lock_state_changed` notification.
- keymap (`keymap.proto` lines 5-41, 147-211):
  - `get_keymap` → layers[{id, name, bindings[{behavior_id, param1, param2}]}], `available_layers`, `max_layer_name_length`;
  - `set_layer_binding(layer_id, key_position, binding)`;
  - `check_unsaved_changes`, `save_changes`, `discard_changes`;
  - `get_physical_layouts` → keys `{width, height, x, y, r, rx, ry}`;
  - `set_active_physical_layout`;
  - add/remove/move/restore layer, set layer name.
- behaviors (`behaviors.proto` lines 5-60): `list_all_behaviors`; `get_behavior_details` → display name plus parameter descriptors (`nil`, `constant`, `range`, `hid_usage {keyboard_max, consumer_max}`, `layer_id`). **The device tells the UI what each behaviour takes**, so the picker is data-driven.
- Errors: `meta.ErrorConditions` includes `UNLOCK_REQUIRED`.

**Unlock.** The keymap must contain a `&studio_unlock` binding, which the user presses (`studio.md` line 45).

**Keycodes.** ZMK uses HID usages. The app bundles `HidUsageTables-1.5.json` and `keyboard-and-consumer-usage-tables.json` (`zmk-studio/src/`) rather than QMK names.

**Relevance to the Voyager.**
- No ZMK Voyager port was found (GitHub search "voyager zmk": only `joshyeram/zmk-config-voyager`, empty, and `carrefinho/forager`, a different 34-key board "inspired by ZSA Voyager", CERN-OHL-P-2.0).
- ZMK does support STM32F303 boards in-tree (`app/boards/olkb/planck/planck_stm32f303xc_zmk.dts`), so a port is conceivable. But ZMK has no per-key RGB matrix equivalent, and the IS31FL3731 would need a driver (**INFERRED**).
- Studio matters for Sextant as a **second protocol family**, for wireless Cornes, Sweeps and Sofles. It does not matter as a Voyager path.

Practical notes:
- **Flashing and reversal.** Every option uses ZSA's bootloader at `0x08000000-0x08001FFF`. The RMK README says the bootloader "lives in protected flash and cannot be overwritten by a firmware image"; that is a community claim. Going back to Oryx means flashing the Oryx `.bin`, for example the user's `hexUrl` (**INFERRED**: no special step).
- **USB identity stays `3297:1977`** in upstream, vial-qmk and RMK builds alike (vial-qmk `keyboards/zsa/voyager/keyboard.json` is byte-identical to upstream's). Sextant must therefore tell firmwares apart by serial number and probes (03 §7.5), not by VID/PID.
  - Corollary: the VIA web app would look up `0x3297*65536+0x1977`, find no definition, and ask for a sideloaded JSON.
- **EEPROM.** The default 1 KB logical EEPROM limits VIA/Vial to about 4-5 layers plus small macro and tap-dance pools (03 §7.6). Neither the Vial port nor the RMK port enlarges it for QMK. RMK reserves the last 4 KB of flash for its own storage (`memory.x` lines 6-15).

### 5.2 Would a VIA/Vial-speaking Sextant also drive Cornes and other boards?

**Yes, with high confidence (INFERRED from the sources below).**

- **Coverage.**
  - Corne v4 ships *by default* with VIA or Vial firmware (`crkbd/docs/firmware/rev4/firmware_en.md` lines 6-26).
  - Older Cornes are flashed `crkbd:via` through Remap (`rev1/firmware_en.md` line 6).
  - Lily58, Sofle, Kyria and Sweep all have VIA and Vial definitions (§3.1).
  - Totals: 2,029 VIA v3 definitions, 634 `vial.json` in vial-qmk, 2,203 VIA userspace keymaps.
- **Vial boards are the easy half.** They self-describe geometry and capabilities, and Sextant needs nothing but the protocol.
- **VIA boards** need the definition by VID/PID. Fetch it at runtime (`/definitions/v3/<vpid>.json` from the VIA site, or from `the-via/keyboards`) or let the user import one.
- **Version handling Sextant must implement:**
  1. VIA protocol 9 to 13.
  2. QMK keycode version: protocol ≤ 12 implies a fixed table; protocol 13+ means asking with `02 06`.
  3. Vial protocol and keycodes v5 vs v6.
  4. Lighting via VIA menus (`qmk_rgblight`, `qmk_rgb_matrix`, custom) or VialRGB.
- **Not covered:** wireless ZMK boards, which need the separate ZMK Studio transport (§4.5), and boards running stock vendor firmware without VIA or Vial.
- **The Voyager itself**, once on Vial or VIA firmware, becomes one more board in this family. In that mode Sextant would use the same code path for the Voyager and a Corne.

### 5.3 What the user would give up by leaving Oryx-generated firmware

The full feature table is 03 §7.7. Summary, with the items specific to this report flagged:

| Lost or changed | Detail |
|---|---|
| **Per-layer RGB key colours** (`ledmap`) | No VIA/Vial equivalent. VIA per-key RGB is single-layer HS on custom channel 0 and unimplemented for the Voyager. VialRGB direct mode is host-driven and volatile (`g_direct_mode_colors` in RAM, `vialrgb.c` line 21). Firmware work is needed to persist per-layer maps (03 §7.7). |

| **Oryx custom keys** | Oryx-generated helpers such as `DUAL_FUNC_n = LT(15, …)` with `process_record_user` (user `keymap.c` line 17) become Vial tap dances, or are lost under plain VIA. | **ZSA firmware cadence** | The ZSA fork (`firmware25`) vs upstream: different keycode versions (0.0.7 vs 0.0.9) and module set. |
| Gains | Instant remaps without reflashing; Vial combos, key overrides, QMK settings at runtime; works offline; one app for the Voyager and the user's future Corne. |

### 5.4 Recommendation for Sextant's architecture

**INFERRED**: synthesis, for the design phase.

1. **Layer the protocols:**
   - `Transport`: raw HID 32-byte reports on 0xFF60/0x61; later CDC-ACM serial and BLE GATT.
   - `Protocol`: `OryxProtocol` (03), `VIAProtocol`, `VialProtocol` (extends VIA), `ZMKStudioProtocol` (protobuf).
   - Pick the protocol after a side-effect-free probe (03 §7.5).
2. **Use one geometry model** (§3.4), keyed by matrix position, with importers for Oryx (built-in ZSA boards), QMK `info.json`, KLE (VIA/Vial) and ZMK physical layouts. The Voyager ships as built-in data (`voyager-matrix-led-map.json`).
3. **Keep two editing modes behind one UI:**
   - "Compile-and-flash" (Oryx-style; keeps every Oryx feature on stock-style firmware);
   - "Live" (VIA/Vial/Studio).
   - Shared features (keycodes, layers, macros, tap-hold) map to both. Mode-specific features (per-layer LED maps vs VialRGB direct; tap dance under VIA) are flagged per board.
4. **Generate keycode tables from QMK hjson per keycodes version.** Don't hand-maintain them.
5. **Choose the app licence early.** GPL-3.0 makes the VIA, Vial and QMK data reusable as-is. A closed licence pushes Sextant to runtime fetching and clean-room tables (§4.7).

### Corrections to apply to the body of this report

1. **§5.1 "USB identity stays 3297:1977 ... RMK builds alike".** This is wrong for RMK, which enumerates as `0x4C4B:0x4643` with serial `vial:f64c2b3c;rmk:…`.
   - A Sextant that finds a "Voyager" by VID/PID would miss an RMK-flashed Voyager.
   - Detect Vial-protocol boards by the serial magic, the way vial-gui does, and take identity from the device's own `vial.json` (`"name": "ZSA Voyager"` for RMK, `"Voyager"` for vial-qmk).
2. **§2.2 Navigator addresses.** State them as 7-bit **0x2C** (Cirque Gen6 trackpad) and **0x28** (SC18IS606 bridge); `0x58`/`0x50` are QMK's pre-shifted forms. Alternatively, label the convention next to every address in the diagram.
3. **§4.4 unlock.** Use the condition "**> 100 ms** since the last decrement **and** all combo keys held; otherwise the counter **resets to 50**". Sextant must poll `FE 07` at intervals of more than 100 ms; vial-gui uses 200 ms, which takes about 10 s. The "floor ~5 s" holds only if every poll lands just after 100 ms.
4. **§4.4 discovery.** The VIA stack is an optional download, not a bundled file. vial-gui accepts only VIA protocol 9, so it does not really drive current VIA firmware (0x0C/0x0D).
5. **§5.2 Corne v4.** Replace "ships *by default*" with "official v4 firmware downloads are VIA and Vial UF2s (flash both halves)".
6. **§2.1 / §0.** ZSA has **16** public repos, 3 of them CI-helper forks.
7. **§4.3 / §5.2 counts.** Use 2,231 VIA userspace `keymaps/via` (not 2,203).
8. **§6 item 6** is resolved: centi-degrees is documented (row 26).
